> الفرع: `arena/a000938c-mishkah-note` · نقطة الانطلاق: `7d20187` (دمج PR #3) · التاريخ: 23 نوفمبر 2026.

## 1. الخلاصة التنفيذية

1. **لا وجود لنسخة 1.0.02** في الشيفرة ولا على GitHub: الإصدار الحالي هو `1.0.01`
   (22 أكتوبر 2026)، والوسم الوحيد `v1.0.01`، وصفحة الإصدار تحمل **تسعة ملفات**
   (ثماني حزم + `SHA256SUMS.txt`).
2. طلبك «تنزيل 1.0.02» يعني عمليًا **تصنيع إصدار جديد**: رفع الرقم في 27 ملفًا
   متعقَّبًا (111 موضعًا)، تحديث حرّاس الاختبار، تحديث سير CI/Release، ثم بناء
   الحزم الثماني ونشرها. لا يوجد زر «تنزيل 1.0.02» قبل ذلك.
3. آلية الإصدار **قوية لكنها مربوطة نصًّا بـ`1.0.01` في 16 موضعًا داخل
   `release.yml`** (ونسخته في `docs/ci/`)، وبفرع الجلسة القديم
   `arena/71ffd864-mishkah-note` في أربعة أماكن. بدون تحديثها لن يعمل أي نشر لـ1.0.02.
4. **يمكنني هنا** بناء والتحقق من: `.deb` + `.whl` + sdist (تحققت فعليًا).
   **لا يمكنني هنا**: `.rpm` وArch وFlatpak وMSI وAppImage النهائي (أدوات غائبة)،
   ولا **رفع** الملفات إلى GitHub (`uploads.github.com` محجوب في هذه البيئة).
   لذلك النشر الفعلي يجب أن ينفّذه GitHub Actions بعد دفع وسم أو تشغيل يدوي.
5. وجدت **13 خللًا برمجيًا محتملًا** (3 منها عالية الأثر: تغيير الاتجاه يعلّم
   المستند كمعدَّل، «نافذة جديدة» غير منفّذة أصلًا، ومنطق «استبدال» مقلوب)
   و**6 فجوات تغليف** (أهمها أن الـAppImage لا يحزم مفسّر Python، وأن sdist
   ناقص ملف AppStream — أثبتُّ الأخير ببناء فعلي).
6. **تحذير تشغيلي**: سير النشر يحذف الإصدارات الأخرى تلقائيًا؛ لحظة نشر
   `v1.0.02` سيُحذف إصدار `v1.0.01` ووسمه. إن أردت الاحتفاظ بنسخة 1.0.01
   للتنزيل، نزّلها قبل النشر.

## 3. كيف يعمل الإصدار في هذا المشروع (خريطة)

```
pyproject.toml (المصدر الوحيد للرقم)
        │
        ├── src/mishkah/__init__.py      → About + --version + عنوان النافذة
        ├── scripts/build-*.sh           → يقرأون الرقم من pyproject
        ├── tools/check_release_assets   → يتحقق من أسماء الملفات الثمانية
        │
        ├── .github/workflows/release.yml
        │      push tag vX  أو  workflow_dispatch(tag)
        │      ├─ validate   : ruff + pytest + verify-packaging + لقطات الشاشة
        │      ├─ 7 وظائف بناء: python, deb, rpm, arch, appimage, flatpak, windows-msi
        │      └─ publish    : يجمع الآثار → check_release_assets → SHA256SUMS
        │                     → يثبّت الوسم → ينشئ/يحرّر الإصدار → يرفع → يحذف القديم
        │
        └── docs/ci/*.yml = نسخة مرجعية يجب أن تبقى مطابقة (diff نظيف الآن)
```

**الفارق الدقيق في الترقيم:** `1.0.01` ليس إصدارًا قانونيًا في PEP 440، فيُطبَّع
تلقائيًا إلى `1.0.2` في أسماء wheel/sdist، بينما تبقى `.deb` و`.rpm` وArch
وAppImage وMSI بالاسم الحرفي `1.0.02`. هذا سلوك مقصود ومدعوم في
`tools/check_release_assets.py` و`scripts/verify-packaging.sh`، لكنه يعني أن
`pip show mishkah-note` سيعرض `1.0.2` بينما نافذة «حول» تعرض `1.0.02`.

## 5. ما يتطلبه 1.0.02 بالضبط (قائمة تحقق)

### 5.1 المصدر (3 ملفات)
- `pyproject.toml` → `version = "1.0.02"`.
- `src/mishkah/__init__.py` → `__version__ = "1.0.02"`.
- `CHANGELOG.md` → قسم `## [1.0.02] — <التاريخ>` بسطور عربية وإنجليزية
  (الحارس يبحث عن `## [1.0.02]` حرفيًا).

### 5.2 حرّاس الاختبار (5 ملفات، وإلا فشل CI فورًا)
- `tests/test_project_meta.py:150,162,164,167` — يقارن `mishkah.__version__`
  و`pyproject` و`PKGBUILD` و`mishkah.1` و`mishkah.wxs` و`spec` وAppStream بـ`1.0.01`.
- `tests/test_cli.py:20,27` — مخرجات `--version`.
- `tests/test_packaging_static.py:30` — رقم مقتطف AppImage.
- `tests/test_manual_builder.py:42` — `builder.version()`.
- `tests/test_release_assets.py` (10 مواضع) — أنماط أسماء الملفات.

**فخّان مهمّان في هذه الحرّاس:**
1. `test_single_release` يفرض **عنصر إصدار واحدًا فقط** في AppStream و**سطر
   changelog واحدًا فقط** في spec RPM. أي أن «تاريخ الإصدارات» ممنوع حاليًا:
   يجب *استبدال* القيود لا إضافتها.
2. التعبير النهائي الذي يمنع ذكر أي رقم سابق هو
   `(?<!\d)1\.0\.(?:0|1)(?!\d)`، وهو **لا يلتقط `1.0.01` نفسها** (لأن `0`
   يتبعها رقم). النتيجة العملية: أي بقايا `1.0.01` في الوثائق أو في
   `release.yml` **لن يمسكها الاختبار**، وستظهر لاحقًا كفشل في خطوة
   `validate` من سير الإصدار أو كملف باسم قديم. لا تعتمد على الاختبار وحده.

### 5.3 التغليف (7 ملفات)
- `packaging/arch/PKGBUILD` → `pkgver=1.0.02`
  (لاحظ أن المصدر يُبنى من `v$pkgver`، فحزمة Arch تحتاج وسم `v1.0.02`).
- `packaging/rpm/mishkah-note.spec` → القيمة الافتراضية `version_override 1.0.02`

- `packaging/common/org.mishkahnote.Mishkah.metainfo.xml` → سمة `<release
  version="1.0.02" date="...">` ونص الوصف.
- `packaging/windows/mishkah.wxs` → **ثلاثة** مواضع (تعليق الأمر، واسم ملف
  الإخراج، و`<?define Version="1.0.02" ?>`).
- `docs/PACKAGING.md` و`README.md` → أسماء الملفات في كل صيغة.

### 5.4 سير العمل (4 ملفات = نسختان × ملفان)
- `.github/workflows/release.yml` + `docs/ci/release.yml` (متطابقان):
  - `on.push.tags: ["v1.0.02"]` (وإلا دفع الوسم لا يشغّل شيئًا).
  - `test "$(python -m mishkah --version)" = "1.0.02"`.
  - `mishkah.__version__ == "1.0.02"` داخل فحص Flatpak.
  - `test "$REQUESTED_TAG" = v1.0.02` و`TAG` الافتراضي `v1.0.02`.
  - `gh api ... refs/tags/v1.0.02` (تثبيت الوسم على مصدر البناء).
  - شرط النشر `contains(..., '[publish 1.0.02]')`.
  - **الفرع**: `arena/71ffd864-mishkah-note` → الفرع الحالي
    `arena/a000938c-mishkah-note` (في: trigger الفرع، شرط النشر، دفع اللقطات).
  - حلقة `Retain the canonical release only` (`for patch in 0 1`) — راجع §6.4.
- `.github/workflows/installers.yml` + `docs/ci/installers.yml`: الفرع في
  `on.push.branches` والنسخة المرجعية.

### 5.5 التوثيق (5 ملفات)
`README.md` (9 مواضع)، `docs/PACKAGING.md`، `docs/PRIVATE_BUILD_GUIDE.ar.md`
(12 موضعًا)، `docs/RELEASE_READINESS.md`، `docs/ci/README.md` — الأخير يوثّق
شروط النشر ويجب أن يصف `v1.0.02` وإلا صار مضلِّلًا.

### 5.6 ما لا يجب نسيانه
- الإصدار الحالي على GitHub سيُحذف تلقائيًا بعد النشر (سياسة الإصدار الواحد).
- `docs/RELEASE_NOTES.md` هو نص صفحة الإصدار حرفيًا (يُنشئه `gh release create
  --notes-file`)؛ يجب إعادة كتابته لوصف 1.0.02، وإلا نُشرت 1.0.02 بوصف 1.0.01.
- `Upload` يحتاج `contents: write`، وهو مضبوط بالفعل في `release.yml`.
- `workflow_dispatch` لا يظهر إلا لملف موجود على الفرع الافتراضي (`main`)؛
  لذلك التشغيل اليدوي من فرع الجلسة غير ممكن قبل الدمج.

## 11. توصية بنطاق «patch حقيقي» لـ1.0.02

لو أردت إصدارًا مبرَّرًا بلا مخاطرة كبيرة على الوظائف الأساسية، هذه الحزمة
الأكثر قيمة/أقل خطرًا:

1. **B1** — منع تغيير الاتجاه من تعليم الملف كمعدّل (أهم إصلاح وظيفي).
2. **B2** — تنفيذ «نافذة جديدة» فعليًا (أو حذف العنصر بدل تركه يكذب).
3. **B3** — تصحيح منطق الاستبدال + احترام خيارات البحث.
4. **M1** — إعادة الفتح بترميز آخر تستبدل المحتوى في التبويب نفسه.
